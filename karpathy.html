Pattern Karpathy 🧠

La méthode qui transforme un projet en cerveau partagé. Sans ça, Claude Code casse votre travail au bout d'une semaine.

⚡ Le pitch en 1 phrase. Vous demandez à Claude de maintenir un wiki interne à votre projet (chaque page, chaque bouton, chaque règle métier), et ce wiki devient la mémoire que Claude relit avant de modifier quoi que ce soit. Résultat : il arrête de casser ce qu'il ne comprend pas.

Le problème : Claude oublie

Quand vous bossez seul avec Claude sur un projet, voici ce qui arrive au bout de 2 semaines :

  • Vous lui demandez de modifier la page "tarifs" → il casse le bouton "Réserver" parce qu'il a oublié à quoi il sert
  • Vous lui demandez de refactorer un composant → il réinvente la roue, dupliquant la logique d'une autre page
  • Vous reprenez le projet 3 mois plus tard → il n'a aucun contexte, vous devez tout réexpliquer
  • Vous changez un détail métier (TVA, prix) → il oublie de propager partout

🚨 Ce n'est pas un bug. Claude n'a pas de mémoire entre sessions. Chaque conversation repart à zéro. Sans pattern, vous lui réexpliquez votre projet à chaque fois. Le pattern Karpathy règle ça.

L'idée d'Andrej Karpathy

Andrej Karpathy (ancien Tesla AI / OpenAI) a popularisé en 2026 cette idée : un projet ne devrait pas être juste du code, mais aussi un wiki maintenu par l'IA elle-même, qui résume, cross-référence et explique chaque partie. Quand l'IA modifie le code, elle met à jour le wiki. Quand elle est appelée à nouveau, elle relit le wiki avant de coder.

C'est la différence entre un stagiaire amnésique et un collègue qui prend des notes.

L'architecture en 3 couches

COUCHE 1

📦 sources/

Immutable. Le code source, les docs originales, les PDF, les transcripts. Claude lit, ne modifie jamais.

COUCHE 2

📚 wiki/

AI-owned. Les notes synthétisées par Claude, une par concept/page/feature. Cross-linked avec [[wikilinks]]. Claude écrit et réécrit ici.

COUCHE 3

📐 CLAUDE.md

Vous-owned. Les règles, le glossaire, la classification, l'index. Vous l'éditez à la main, Claude le relit comme une bible.

Concrètement, ça ressemble à quoi ?

mon-projet/
├── CLAUDE.md            ← règles du projet (vous écrivez)
├── sources/             ← code, PDFs, transcripts (immutable)
│   ├── src/
│   ├── docs/
│   └── normes/
├── wiki/                ← notes IA (Claude écrit et met à jour)
│   ├── pages/
│   │   ├── accueil.md
│   │   ├── tarifs.md
│   │   └── contact.md
│   ├── composants/
│   │   ├── bouton-reserver.md
│   │   └── formulaire-devis.md
│   ├── business-logic/
│   │   ├── tva.md
│   │   └── pricing-rules.md
│   └── log.md           ← journal append-only des changements
└── MAP.md               ← index auto-généré du wiki

Le workflow quotidien

  1. /init le projet

    Claude scanne sources/ et écrit le wiki/ initial. Compte 5-15 notes par feature.

    Bootstrap d'un projet avec wiki
    Lance le pattern Karpathy sur ce projet. Crée la structure wiki/ avec une note par page, par composant, par règle métier. Cross-link avec [[wikilinks]]. Génère MAP.md et log.md à la racine.

  2. /ingest quand vous ajoutez une source

    Nouveau PDF, nouvelle norme, nouvelle interview ? Claude la lit et met à jour les notes wiki concernées.

    Ingest d'une nouvelle source
    Ingest le PDF sources/normes/dtu-25-41.pdf dans le wiki selon le pattern Karpathy. Met à jour les notes existantes liées, crée les nouvelles, ajoute une entrée dans log.md.

  3. /lint avant chaque session

    Claude vérifie le wiki : orphelins (notes pas liées), wikilinks cassés, notes périmées, contradictions.

    Lint du wiki
    Lint le wiki : trouve les notes orphelines (jamais référencées), les wikilinks cassés, les contradictions entre notes, les notes obsolètes (last-updated > 30j).

  4. /query pour répondre vite

    Au lieu de re-grepper tout le code, Claude lit le wiki et répond instantanément.

    Question rapide
    D'après le wiki, qu'est-ce que fait exactement le bouton "Réserver" et de quoi il dépend ?

  5. /digest hebdomadaire

    Claude produit un résumé de la semaine : ce qui a changé, ce qui est en suspens, ce qui doit être nettoyé.

    Digest hebdo
    Lis log.md des 7 derniers jours et fais-moi un digest : quels changements, quelles décisions, quelles dettes techniques. Format markdown lisible en 30 secondes.

Wiki Karpathy vs RAG : la bombe atomique du combo

Beaucoup de gens connaissent les RAG (Retrieval Augmented Generation). Karpathy n'est pas un remplacement, c'est un complément. Voici la différence :

RAG (recherche sémantique) Wiki Karpathy
Format Chunks de texte vectorisés Notes markdown cross-linked
Recherche Similarity search (cosine) Lecture directe + suivi des [[liens]]
Contexte Chunks isolés (perd les liens) Réseau de notes (préserve les liens)
Maintenance Re-vectoriser à chaque MAJ Claude maintient lui-même
Précision Bonne sur gros volumes Excellente sur projet précis
Coût Embeddings + DB vectorielle Zéro (juste des .md)
Idéal pour Textes de loi, papiers scientifiques, gros corpus externes Knowledge interne projet : code, pages, business logic, décisions

Pourquoi le combo est imbattable

RAG

Pour les gros corpus externes

Vous avez 500 PDFs de normes DTU, 10 000 articles juridiques, des transcripts d'interviews clients. Le RAG les indexe tous. Claude pose une question, le RAG retourne les passages les plus pertinents.

KARPATHY

Pour le contexte projet

Le wiki Karpathy capture votre compréhension du projet : pourquoi le bouton fait ça, quel concurrent on imite, quelle décision a été prise en réunion. Le contexte humain que le code seul ne dit pas.

💎 Le combo gagnant. Claude utilise le wiki Karpathy pour comprendre votre projet en 30 secondes, puis interroge le RAG uniquement quand il a besoin de fouiller un corpus volumineux (normes, lois, papiers). Vitesse + précision + contexte. C'est ça, la "bombe atomique".

Cas d'usage concrets pour AUTAF

🏗️
Site AUTAF (refonte / évolution)
Wiki Karpathy = note par page (accueil, services, contact), note par composant (bouton CTA, formulaire devis), note par règle business (politique TVA, conditions).

Quand vous demandez "ajoute une section témoignages", Claude relit les notes voisines, comprend le style maison, et propose une section cohérente.

🎯
Base prospects & contacts
Wiki Karpathy = note par prospect important (historique, décideur, sensibilité prix). Sources = exports Apify, transcripts d'appels.

Quand vous reprenez le suivi 3 mois après, Claude rouvre la note et vous résume le contexte en 5 lignes.

📹
Personal brand TikTok / LinkedIn
Wiki = note par "pilier" de contenu, note par format gagnant, note par audience. Sources = analytics, transcripts vidéos, commentaires.

Quand vous demandez "fais-moi un calendrier édito 30 jours", Claude relit le wiki et reproduit ce qui a marché.

⚖️
Veille normes / juridique (RAG + Karpathy)
RAG sur 500 PDFs DTU + Karpathy qui synthétise les normes pertinentes en notes courtes thématiques.

Quand un client demande "c'est conforme DTU 25.41 ?", Claude répond en 10 secondes via le wiki, et descend dans le RAG si besoin de précision.

Le mini-template pour démarrer

Voici le prompt à coller dans Claude Code pour bootstrap le pattern Karpathy sur n'importe quel projet :

Bootstrap pattern Karpathy (à copier-coller)
Initialise le pattern Karpathy sur ce projet selon ces règles : 1. Crée un dossier `wiki/` à la racine avec sous-dossiers : pages/, composants/, business-logic/, decisions/ 2. Crée `MAP.md` à la racine : index de toutes les notes wiki 3. Crée `log.md` à la racine : journal append-only des changements (date + auteur + résumé) 4. Crée `CLAUDE.md` à la racine avec : - Les règles du projet (langue, style code, conventions) - Le glossaire (acronymes, termes métier) - La classification des notes wiki (quel type va où) 5. Scanne le projet existant et génère une 1ère salve de notes wiki (1 par page, 1 par composant clé) 6. Chaque note doit avoir un frontmatter YAML (name, type, description, last-updated) et cross-linker avec [[autres-notes]] 7. À la fin, ajoute la 1ère entrée dans log.md résumant le bootstrap Format des notes : markdown, max 100 lignes par note, toujours en français.

Les règles d'or à connaître

Règle 1. Le wiki est la source de vérité du contexte projet, pas du code. Le code reste la source de vérité du comportement. Si les deux divergent, faites confiance au code et corrigez le wiki.

Règle 2. Une modification de code = une mise à jour du wiki. Claude doit faire les deux dans le même mouvement. Si vous oubliez, le wiki devient inutile.

Règle 3. log.md est append-only. On n'efface jamais. Une entrée par changement significatif. Ça devient votre journal de bord.

Règle 4. Lint hebdomadaire obligatoire. Une note non liée = un orphelin. Un orphelin = du bruit. Claude doit nettoyer ou rattacher.

Règle 5. CLAUDE.md = la bible. Vous l'éditez à la main, Claude le relit en premier à chaque session. Y mettre vos préférences, vos interdits, vos décisions stratégiques.
